1. Relational Schema of the Database

Forkcast is built on twelve relations. The schema below is the working DDL for the project, written for PostgreSQL. Interfaces and SERIAL surrogate keys are used throughout so that no natural key has to be propagated as a foreign key. 

-- Core user table. ISA collapsed into one table with a role flag
-- instead of three separate tables.
CREATE TABLE Student (
    student_id   SERIAL PRIMARY KEY,
    name         VARCHAR(100) NOT NULL,
    email        VARCHAR(100) NOT NULL UNIQUE,
    year         VARCHAR(20),
    major        VARCHAR(100),
    role         VARCHAR(20) NOT NULL DEFAULT 'regular', -- 'regular' or 'admin'
    admin_privileges       VARCHAR(100),   -- set only when role = 'admin'
    profile_visibility     VARCHAR(20) DEFAULT 'public',
    notification_settings  JSONB
);

CREATE TABLE DiningHall (
    dining_hall_id SERIAL PRIMARY KEY,
    name           VARCHAR(100) NOT NULL UNIQUE,
    location       VARCHAR(200),
    hours          VARCHAR(200)
);

CREATE TABLE Menu (
    menu_id        SERIAL PRIMARY KEY,
    dining_hall_id INT NOT NULL REFERENCES DiningHall(dining_hall_id),
    date           DATE NOT NULL,
    meal_period    VARCHAR(20) NOT NULL,
    description    TEXT,
    UNIQUE (dining_hall_id, date, meal_period)
);

CREATE TABLE Dish (
    dish_id     SERIAL PRIMARY KEY,
    name        VARCHAR(150) NOT NULL,
    category    VARCHAR(50),
    ingredients TEXT[],
    allergens   TEXT[]
);

CREATE TABLE MenuDish (
    menu_id INT REFERENCES Menu(menu_id),
    dish_id INT REFERENCES Dish(dish_id),
    PRIMARY KEY (menu_id, dish_id)
);

CREATE TABLE Rating (
    rating_id    SERIAL PRIMARY KEY,
    student_id   INT NOT NULL REFERENCES Student(student_id),
    dish_id      INT NOT NULL REFERENCES Dish(dish_id),
    menu_id      INT REFERENCES Menu(menu_id),  -- ties a rating to a specific day/serving
    score        NUMERIC(3,1) NOT NULL,
    is_synthetic BOOLEAN NOT NULL DEFAULT FALSE,
    created_at   TIMESTAMP NOT NULL DEFAULT now(),
    UNIQUE (student_id, dish_id, menu_id)
);

-- With media/Giphy attachments, this is the comments advanced function
CREATE TABLE Comment (
    comment_id        SERIAL PRIMARY KEY,
    student_id        INT NOT NULL REFERENCES Student(student_id),
    dish_id           INT REFERENCES Dish(dish_id),
    content            TEXT NOT NULL,
    media_urls         TEXT[],   -- image and Giphy links attached to this comment
    created_at          TIMESTAMP NOT NULL DEFAULT now()
);


CREATE TABLE DishSuggestion (
    suggestion_id SERIAL PRIMARY KEY,
    student_id    INT NOT NULL REFERENCES Student(student_id),
    content       TEXT NOT NULL,
    upvotes       INT NOT NULL DEFAULT 0,
    downvotes     INT NOT NULL DEFAULT 0,
    created_at    TIMESTAMP NOT NULL DEFAULT now()
);

CREATE TABLE Survey (
    survey_id            SERIAL PRIMARY KEY,
    student_id           INT NOT NULL UNIQUE REFERENCES Student(student_id),
    date_taken           DATE NOT NULL,
    dietary_restrictions TEXT[],
    favorite_cuisines    TEXT[],
    other_preferences    TEXT
);

-- Recommendation advanced function, this pair is the actual engine.
-- Both are caches recomputed periodically from Rating, not hand maintained.
CREATE TABLE DishPreference (
    student_id       INT REFERENCES Student(student_id),
    dish_id          INT REFERENCES Dish(dish_id),
    preference_score NUMERIC(5,3) NOT NULL,  -- time-weighted R_u,X
    last_updated     TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (student_id, dish_id)
);

CREATE TABLE DishCorrelation (
    dish_id_1          INT REFERENCES Dish(dish_id),
    dish_id_2          INT REFERENCES Dish(dish_id),
    correlation        NUMERIC(5,4) NOT NULL,   -- rho_XY
    shared_rater_count INT NOT NULL,            -- n_XY
    last_updated       TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (dish_id_1, dish_id_2),
    CHECK (dish_id_1 < dish_id_2)  -- store each unordered pair once
);

Keys and functional dependencies

Every relation below is in BCNF — every determinant is a candidate key, and where a UNIQUE constraint is declared the surrogate and natural keys determine each other.

Functional dependencies derived from the keys and constraints declared above.

email		 student_id → name, email, year, major, role, admin_privileges, profile_visibility, notification_settings
email → student_id (and therefore all remaining attributes, transitively)

name → dining_hall_id, location, hours

(dining_hall_id, date, meal_period) → menu_id, description

DishCorrelation (dish_id_1, dish_id_2) (dish_id_1, dish_id_2) → correlation, shared_rater_count, last_updated — a symmetric relation, so only the pair with dish_id_1 < dish_id_2 is stored; the reverse pair is implied.

Referential (inclusion) dependencies

The foreign keys also impose inclusion dependencies of the form R.A ⊆ S.B: Menu.dining_hall_id ⊆ DiningHall.dining_hall_id; MenuDish.{menu_id, dish_id} ⊆ Menu.menu_id × Dish.dish_id; Rating.{student_id, dish_id, menu_id} ⊆ Student.student_id × Dish.dish_id × Menu.menu_id; Comment.{student_id, dish_id} ⊆ Student.student_id × Dish.dish_id; Survey.student_id ⊆ Student.student_id; DishSuggestion.student_id ⊆ Student.student_id; DishPreference.{student_id, dish_id} ⊆ Student.student_id × Dish.dish_id; and DishCorrelation.{dish_id_1, dish_id_2} ⊆ Dish.dish_id × Dish.dish_id.

3. Data Sources

We will get the menu data from https://dining.nd.edu to see previous offerings at the dining hall. This data can be obtained by scraping the site, and it gives us:

  • Dish name
  • Dining location
  • Meal periods
  • Dates

Ratings, surveys, and comments will be provided by students.

5. Project Timeline & Milestones

  1. Oct. 1–7 Database Setup & Data Collection

    Create all database tables, constraints, keys, and relationships. Develop scripts for collecting/importing real-world data.

  2. Oct. 8–14 Data Population & Backend Integration

    Populate the database with real data and connect the web application to the database. Target 10,000+ data items across at least 5 relations.

  3. Oct. 15–21 Basic Database Functions

    Implement insertion, searching/querying, updating, and deletion. Test SQL queries and database interactions.

  4. Oct. 22–28 Initial Frontend & Integration

    Build the main user interface and connect frontend actions to the database-backed functionality. Begin implementing the two advanced functions.

  5. Oct. 29–Nov. 3 Initial Demo Preparation

    Test the complete basic workflow, fix bugs, verify the real dataset, and prepare the 15-minute demonstration. Finalize plans/designs for both advanced functions.

  6. Nov 4th Initial Demo

    Demo its application in its initial working status.

    • Real data in the database — 10,000 or more items of data across 5 or more different relations.
    • Show how to insert/update/delete records to the database.
    • Show how to search the database and list or print returned results. One of the queries must involve join of multiple tables.
    • Talk about your plan for the next stage of the project, including what advanced functions you plan to support.
  7. Nov. 5–15 Advanced Function 1

    Implement, integrate, and test the first advanced function.

  8. Nov. 16–25 Advanced Function 2

    Implement, integrate, and test the second advanced function.

  9. Nov. 26–Dec. 2 Final Integration & UI

    Integrate both advanced functions, improve UI/UX, add interesting database queries including a multi-table join, and perform system-wide testing.

  10. Dec. 3–6 Final Testing & Documentation

    Fix remaining bugs, verify all requirements, prepare the final report, and record the 2-minute demo video.

  11. Dec. 7–9 Final Demonstration

    Present the 2-minute video demonstrating the completed system and its major features.
